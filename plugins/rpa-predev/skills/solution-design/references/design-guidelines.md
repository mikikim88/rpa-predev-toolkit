# RPA 솔루션 설계 가이드

## 1. 구조 선택

| 조건 | 권장 구조 |
|------|-----------|
| 처리 건수 많음(월 100건↑), 건별 재처리 필요, 여러 봇 병렬 실행 | **Dispatcher – Performer** (큐 기반) |
| 건수 적음, 단일 실행으로 끝남 | **단일 프로세스** (Init → Process → End) |
| 사람이 실행 버튼을 누름, 판단 단계가 중간에 있음 | **Attended(RDA)** + 사람 입력 폼 |

기본 모듈: Init(설정·앱 실행·로그인) → GetData / Dispatcher → Process / Performer → Report → End.
모듈 하나는 한 가지 책임만 가진다. 시스템별 화면 조작은 재사용 가능한 컴포넌트로 분리한다.

## 2. 플랫폼별 용어

| 개념 | UiPath | Power Automate Desktop | Automation Anywhere | Brity RPA |
|------|--------|------------------------|---------------------|-----------|
| 관리 콘솔 | Orchestrator | Power Automate (Cloud) | Control Room | Brity Designer/Orchestrator |
| 작업 큐 | Queue | Work Queue | Workload Queue | Queue |
| 공유 설정값 | Asset | 환경 변수 | Global Value | 환경 변수 |
| 자격증명 | Credential Asset | Credential (Azure Key Vault) | Credential Vault | Credential |
| 표준 템플릿 | REFramework | — | Bot Framework | — |

플랫폼이 정해지지 않았으면 사용자에게 묻고, 미정이면 중립 용어(설정/큐/자격증명 저장소)로 작성한다.

## 3. 예외 처리 설계 원칙

- **Business Exception**: 데이터·업무 규칙 위반. 재시도해도 결과가 같으므로 **재시도하지 않고** 해당 건을
  예외 처리한 뒤 담당자에게 알린다. PDD의 "비즈니스/데이터" 예외가 여기에 해당한다.
- **System Exception**: 화면 지연, 앱 다운, 요소 미발견. **스크린샷 → 앱 재기동 → N회 재시도**,
  초과 시 실패 처리 후 운영팀 알림. PDD의 "시스템" 예외가 여기에 해당한다.
- **중복 처리 방지 (멱등성)**: 저장 전에 "이미 처리됐는지"를 확인한다 (전표번호 존재 여부, 큐 Reference 고유키).
  재시도 때 같은 전표가 두 번 생성되지 않게 하는 것이 가장 중요한 설계 포인트다.
- PDD의 예외 항목은 **빠짐없이** SDD 예외 표로 옮기고 감지 방법과 재시도 횟수를 구체화한다.

## 4. 설정 · 보안

- 경로, 수신자, 허용 오차, URL처럼 바뀔 수 있는 값은 코드에 넣지 않고 Config/Asset으로 뺀다.
- 계정 정보는 플랫폼 자격증명 저장소에 보관한다. 봇 전용 계정 + 최소 권한을 원칙으로 한다.
- 로그·스크린샷·결과 파일에 개인정보·계좌번호가 남지 않도록 마스킹 방안을 명시한다.
- 망분리, 공동인증서, OTP, SAP GUI Scripting 허용 여부는 IT·보안 확인 항목으로 `open_questions`에 넣는다.

## 5. 테스트 시나리오 도출

- 정상 흐름 1건 이상 + **PDD 예외 항목마다 최소 1건**의 예외 시나리오를 만든다.
- 재시도·중복 방지 검증 시나리오(처리 중 앱 강제 종료 → 재실행 시 중복 없음)를 반드시 포함한다.
- 볼륨 테스트(실제 월 건수 규모)로 예상 수행시간을 검증한다.

## 6. 일정 (기본값, 조정 가능)

설계 확정 1주 → 개발 2–4주(모듈 수·시스템 수에 비례) → 통합 테스트/UAT 1–2주 → 운영 이관·병행 운영 1회.
